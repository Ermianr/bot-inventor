# ROADMAP

What the project plans and in which order. There is no version target and no dates. How to work on it is in [`CONTRIBUTING.md`](CONTRIBUTING.md); the decisions behind it are in [`DECISIONS.md`](DECISIONS.md).

**Stage: building the base.** The architecture, decisions, tooling and contribution rules are written, the repository is public, and the workspace skeleton (M0), the project model (M1), the payload codec (M2), the expression engine (M3), compile (M4), the runtime core (M5), the variables with their storage (M6), the Discord adapter (M7), the runner (M8), the export (M9), the editor (M10a and M10b), the condition builder (M11a and M11b) and the backend and the interface of local run and export (M12a and M12b) are done. A bot runs from the command line with `runner --payload`, and `exporter::export` writes the folder of an exported bot; the tests of local run and export in the real app (M12c) are next.

## 1. Vision

A cross-platform, open source desktop application to build bots **without code** from a node editor. The first platform is Discord; the design allows others later. The app runs the bot locally with live logs, or exports it as a standalone executable. Linux comes first. Priorities: security, then functionality, then performance and low memory.

Three small reference bots drive the first milestones: **Ping** (`/ping` replies), **Welcome** (greets new members and assigns a role) and **Moderation** (`/kick`, `/ban`, `/timeout` with permission checks, an error path and a log message).

## 2. Milestones

The single unit of planned work: a capability stage with a definition of done (DoD), sized for one pull request (a few days; if it grows past about a week it is split). Statuses: `draft` (a sketch of the DoD), `ready` (criteria agreed in full, can be started), `in progress`, `done`, `dropped`. The rules for taking and finishing one are in `CONTRIBUTING.md` §3.2. The full criteria of a milestone are written before it starts; a DoD is shown by a test or a command, not by a statement.

### Done

- **M0. Workspace skeleton** (#1). The Rust and pnpm workspace, `cargo xtask` (`dev`, `lint`, `test`, `build`, `layers`, `bindings`), CI on Linux (lint, tests, bindings check, Conventional Commits on the title and the commits), the empty Svelte app in a Tauri window with a restrictive CSP and one allowed command, and the baseline configuration files.
- **M1. Project model** (#2). The project side of the `graph` crate. `Project::load` and `Project::save` read and write the `.botproj` folder (`bot.botproj`, `flows/*.flow.json`, a generated `.gitignore`) with a stable key order, through a temporary file and a rename; the `ping` sample (`crates/graph/tests/samples/v1/ping/`) saves back to identical bytes. Node ids, flow names, aliases, port names and variable names are validated types. A newer `format_version` is refused with a message that says to update the app; older ones go through a table of migration steps (empty for now), and a test requires a sample for every version. Symbolic links, non-regular files, files over 4 MiB and more than 256 flows are refused, and a table of bad inputs (invalid JSON, wrong types, missing and unknown fields, invalid UTF-8, deep nesting, bad names) returns typed errors that name the file and never panic. The payload types and codec are M2; the checks on the graph are M4; the TypeScript bindings of these types come with the editor (M10a). The backup copy before a migration comes with the first real migration.
- **M2. Payload codec** (#4). The payload side of the `graph` crate. `Payload` has the contents of `ARCHITECTURE.md` §3.2 (version, app version, flows with their nodes and lines as index adjacency, expression sources as text, the event table, the command definitions with their hash, the variables and the requirements) and no editor data; `check` verifies that every index points inside its list. `Payload::encode` writes MessagePack with field names, compressed with zstd and its content checksum, and gives the same bytes for the same payload; `Payload::decode` reads it back. Bad payloads (empty, truncated at any length, a damaged byte, not zstd, not MessagePack, trailing bytes, wrong types, missing and unknown fields, bad names, an index that points nowhere) return a typed `PayloadError` and never panic; the version is read before the rest, so a newer one says to update the app, an older one to export again, and version 0 is invalid. A payload is refused above 16 MiB compressed, 64 MiB decompressed (a zstd bomb is read only up to the limit, and a frame asking for a larger window is refused) or nested deeper than 128 levels, and `encode` refuses what `decode` would. The container footer (`BOTINVPL`, container version, payload length) is written by `write_container` and found at the end of a `Read + Seek` by `read_container`, which tells a file with no footer apart from a footer that cannot be trusted. `dump_json` and `cargo xtask dump <file>` print a payload, or the payload at the end of an exported bot, as JSON; `runner --dump` will use the same function in M8. `tests/payload_samples/v1/` holds the Ping payload and its dump, and a test requires a sample for every version. The compile step that fills a payload is M4, the node catalog that gives the settings a meaning is M5, and the `cargo-fuzz` target for the decoder comes with the other fuzz targets.
- **M3. Expression engine**. The `expr` module of the `runtime` crate. `ExpressionEngine` is a trait whose only implementation, `CelEngine`, uses `cel` (`=0.15.0`, no default features) from one module; the features and the closed list of operators and functions are in `DECISIONS.md`. A source is compiled once into a `Send + Sync` expression and evaluated against a `Scope` (`event`, `steps`, `vars`, `error` as plain data) in a child of one shared base context. `Template` splits plain text with `{{ expression }}` segments, understanding quoted text and nested braces (`{{ '{{' }}` writes a literal `{{`); what the segments produce, including text from Discord users, is inserted as text and never evaluated. `References` lists the full paths an expression reads (`event.user.id`, `steps.<alias>.<output>`, `vars.<scope>.<name>`, `error.kind`), stopping at a dynamic index, and the named functions it calls; macro variables are not references and an unknown root is an error. Limits on the source, nesting, operators, macro nesting, the scope and the result are in `ARCHITECTURE.md` §6, with a test for each, and a test runs the largest allowed chains on a 512 KiB stack. Evaluation errors carry no values. A table of bad inputs and `proptest` runs over arbitrary text find no panic, and the real conditions of Welcome and Moderation (role and permission checks, role hierarchy, text and number comparisons, an optional reason with a default, and the log templates) evaluate to the expected value. Checking references against triggers, nodes and declarations is M4.
- **M4. Compile and validate** (#6). The compile step of `ARCHITECTURE.md` §3.3, in the `runtime` crate, with the node schemas it needs. `runtime::catalog` has `NodeSpec`, `FieldSpec`, `FieldKind`, `PortSpec`, `OutputSpec`, `NodeRequires` and `TriggerSpec` as in §5.2 and a `Registry` keyed by type and `type_version` (a duplicate key is refused); it declares the schemas, with no executor, of `discord.slash_command`, `discord.reply` and `logic.branch`. `compile(&Project, app_version)` returns a `Report` with the diagnostics in a fixed order, the variables each node reads and, only when there is no error, the `Payload`; a warning does not block it. A diagnostic has a severity, a stable code, the flow, the node id, the field path (`lines[n]` for a line) and a message that names the field and the limit and never a setting's value. Tests cover each structure rule (duplicate ids and aliases, unknown nodes, ports and versions, a line into the trigger, a repeated line, no trigger or two, an unreachable node, cycles), the settings (missing, unknown, wrong type, text and number limits, closed lists, asset paths), the expressions (syntax, `event.*` against the trigger and its options, `steps.*` as always, sometimes or never before the node, `vars.*` against the declarations, `error.*` against the `error` ports) and the variable declarations. The Discord limits each have a test at the limit and one over it, apart from the 8000 characters, which only a command with more than 25 options reaches, and the options limit is reported at the same time. A flow is limited to 2048 nodes and 8192 lines, every pass is iterative, and a test compiles the largest flow on a 512 KiB stack. `Requirements` are the sorted union of what the nodes in use declare; a template with no `{{ }}` segment is not stored as an expression; `CommandDef::hash` is the SHA-256 of the definition with its keys in order, and a test changes one option and sees it change. The `ping` sample compiles with no diagnostic to the payload committed in `tests/payload_samples/v1/`, which replaced the hand-written one, and the order of nodes and lines in the files does not change the bytes. A snapshot test (`insta`) fixes the message of every code, apart from `invalid-payload`, a guard on `Payload::check` that no project reaches. `proptest` runs find no panic on arbitrary projects, compile a random valid flow with every index in range, find a cycle whenever a line goes back to an ancestor, and give the same result when the nodes and lines are shuffled. The node rows of section 4 stay *Now* until M5 gives them an executor.
- **M5. Runtime core** (#7). The run side of the `runtime` crate. `Platform` (`platform` module) is the trait the runtime sees, with `Event`, `Reply` and a closed `PlatformError` that carries no data from the platform, and `MockPlatform` records every action and can fail the next ones or wait. A `Runtime<P>` is built from a `Payload` (`Runtime::new`, or `with` for the engine and the limits): it finds the schema of every node, compiles every expression and template once, and refuses with a typed `RuntimeError` what it cannot run. `dispatch(event)` starts one tokio task per flow the event reaches (a slash command reaches the flow of that command, any other event the flows its kind is routed to) and `drain()` waits for them. A run holds the event, the outputs of the steps so far and the declared variables (every scope reads its `initial` value until storage arrives in M6), and walks the flow with the lowest-index node first, so a node runs once, after every node before it that runs. The nodes are in `runtime::nodes`, each with its schema and its executor: `discord.slash_command` (sets the visibility of the replies), `discord.reply` (the first reply is the response, the next ones are follow-ups, with no mention allowed and a content of 1 to 2000 characters once written; it publishes `message_id`) and `logic.branch`; a test requires that every schema has an executor and the other way round. A node that fails goes through its `error` port with `error.kind` (`expression`, `invalid_value`, `missing_permissions` or `platform`) and a message that names the setting and never its value; with no line out of `error` the run fails, the detail goes to the `RunLog` and, if the interaction has no response yet, the user gets one generic ephemeral message. The limits are 64 simultaneous runs (an event past it is dropped with a warning), 500 steps and 60 seconds per run, each with a test at the limit and one over it, the largest flow runs on a 512 KiB stack, and a `proptest` run finds no panic with arbitrary event data. Every node has a bad-input test over payloads that skip compile. The first "Adding a node" recipe is in `CONTRIBUTING.md` §8. The 2-second deferral is M7, the JSON log format and signals are M8, and the other nodes of section 4 are M6 and M13. `tokio` (`rt`, `sync`, `time`) is the only new dependency.

- **M6. Variables and storage**. Persistent variables, from the `Storage` trait to a real SQLite file. `runtime::storage` has the `Storage` trait (`check_variables`, `get_many` in one batch, `set`, `add` and `reset_variable`), the `StoredValue` an integer, a decimal, a text (at most 4000 characters) or a boolean, so a value of another shape cannot be stored, and `MemoryStorage` for tests. `Runtime<P, S>` takes the storage as a second type parameter that defaults to `MemoryStorage` (`Runtime::with_storage`; the M5 constructors keep working). The new crate `storage-sqlite` puts one `rusqlite` connection (`bundled`, no default features) on a dedicated thread, with WAL, `synchronous = FULL`, foreign keys, a 1 MiB cache and a 5 second busy timeout; the file is created with mode 0600 and a link or a folder is refused. The tables are in `ARCHITECTURE.md` §8: a value references the recorded type of its variable, so the database itself refuses a write of another type. The schema version is `PRAGMA user_version` and `MIGRATIONS[n]` takes version `n` to `n + 1`: a newer database is refused with a message that says to update the app, a database of another program is refused, and an older one is copied first (`VACUUM INTO`, `bot.sqlite.v1.bak`, never over an existing file) and migrated in one transaction. When the bot starts, `check_variables` records the declared type of each persistent variable: integer to decimal converts the stored values, any other change is refused with a message that names the variable and `--reset-variable <scope>.<name>`, unless nothing is stored for it, and the check is all or nothing. `reset_variable` deletes the values and the recorded type of one variable (the flag is wired to it in M8). In a run, the variables a node reads (the compile step's list, computed again from the compiled expressions) are fetched in one batch just before it runs and once per run, and the writes of the run update that copy; a missing row reads as `initial` (a decimal declared with a whole number reads as a decimal), and `run` variables never touch the storage. The key comes from the event: `event.guild.id` for `server`, that and `event.user.id` for `member`, `event.user.id` for `user`, each a Discord id of at most 20 digits; an event without them fails the node with `invalid_value`. `data.set_variable` has `variable` (`scope.name`), `operation` (`set` or `add`) and `value` (an expression), and publishes `value`, the new value; `add` is the atomic counter (one statement, so no run and no connection comes between the read and the write) and fails with `invalid_value` instead of wrapping on an overflow. Compile reports a variable that is not declared (`unknown-variable`) and an `add` on text or a boolean (`add-to-non-number`). A storage failure sends the node to its `error` port with the new `error.kind` `storage`; its message names a variable at most and never a value or the detail of the database. The tests: a value survives closing and reopening a real file; 64 tasks, and two connections, adding at once lose no count; a sample database of every schema version opens (a test requires one per version) and a stand-in migration shows the backup, the single transaction and the refusal of a newer database; a type mismatch names the variable; integer to decimal keeps the values; `reset_variable` touches only its variable; `member` and `user` values do not mix; the same behaviors run on `MemoryStorage`; every error of the node has a bad-input test over payloads that skip compile, and a `proptest` run with arbitrary values and ids finds no panic. `rusqlite` is the only new dependency (MIT, with the SQLite it builds, which is public domain).

- **M7. Discord adapter**. The new crate `platform-discord` implements `Platform` on twilight (`0.17.1`) and feeds a `Runtime`. `Platform::defer` is new: the run defers an interaction 2 seconds after it starts if there is no response, with the visibility of the command node; the timer and the replies share the state of the response behind a lock held while a message is sent, the first message after a deferral completes it and the rest are follow-ups, a deferral that fails is logged and the run goes on, and a run that fails after a deferral sends the generic message in place of "thinking" (`crates/runtime/tests/run_defer.rs`, with a paused clock). `event::normalize` turns a slash command into an `Event` (Discord ids as text, `event.member.permissions` as permission names, `event.timestamp` from the interaction id, options as `{ name: value }`) and refuses what is not a command, options of a kind the editor does not define, text past 6000 characters and names out of range, with a table of hostile inputs. `commands::plan` compares the registered commands with the payload field by field (not by the hash), so a second start sends no call, a change sends only that command, a removed command is deleted and a command edited by hand is put back; with `DISCORD_DEV_GUILD_ID` the commands go only to that server. `intents` maps the names in `Requirements` to gateway intents, event types and cache resources (an unknown name is an error, and there is no cache when none is asked for). `Discord::connect` checks the token with one request, `Discord::run` reads the gateway and calls `dispatch` (a flow never runs in the loop), waits longer after each error up to a minute, and closes on a signal in about 75 ms. The interaction token stays in the adapter (`Token` has no `Display`, and no `Debug` shows a token). A 403 is `MissingPermissions` and anything else `Failed`; the requests are tested against a fake HTTP server (routes, bodies, the 403, the deferral). `crates/platform-discord/examples/serve.rs` runs a bot from `--payload` or `--project`, with the token read from an env file. Checked by hand on a real test server with `DISCORD-TEST.md`: rows 1, 2 and 3 (created, `Pong!`, a second start with no change), a clean stop, and the deferral (a 4 second delay before the reply showed "thinking" from second 2 and `Pong!` replaced it with no second message). Not run by hand: rows 4, 5, 7 and 9, which the unit and request tests cover. New dependencies: the `twilight-*` crates (`gateway`, `http`, `model`, `cache-inmemory`), `rustls` with `ring` (twilight leaves the crypto provider to the application and panics without one), and `tokio` `macros`; `deny.toml` allows `ISC` and `CDLA-Permissive-2.0`. The runner binary is M8.

- **M8. Runner**. The new crate `crates/runner` (binary `runner`) wires `runtime`, `platform-discord` and `storage-sqlite`, and replaces the `serve` example. The commands are `--payload <file>`, `--dump` (`graph::dump_json`), `--check` (payload, `.env`, assets, intents and the nodes, without connecting), `--reset-variable <scope>.<name>` (the bot must declare it), `--version` and `--help`; without `--payload` it reads the `BOTINVPL` footer of its own executable, and a test appends a payload to a copy of the runner. The paths come from `BOT_INVENTOR_PAYLOAD`, `BOT_INVENTOR_ENV_FILE`, `BOT_INVENTOR_ASSETS_DIR` and `BOT_INVENTOR_DATA_DIR`, or from next to the executable. The token is read only from `.env` (which warns when others can read it) and is no argument. Every asset is checked again at start with `runtime::compile::unsafe_asset_path` (now public), so `..`, absolute paths and links out of `assets/` are refused. `data/` is created with mode 0700. The log is JSON lines on standard output (`ARCHITECTURE.md` §9.2): `LogRecord` has a new `run` number, the token (and its JSON-escaped form) is redacted from every value and from the finished line, and at most 100 lines are written per second, with one line that says how many were dropped. `SIGTERM` and `SIGINT` stop the bot, close the gateway, wait up to 5 seconds for the runs in progress and exit `0`; during the connection they stop it there. The exit codes are `0` (clean), `2` (configuration: arguments, `.env`, token, server id, assets, intents, a changed variable type, a newer database), `3` (payload version) and `1` (anything else); a failure to start is one `error:` line on standard error. `Discord::connect_via` sends the HTTP requests to a stand-in server (`BOT_INVENTOR_DISCORD_PROXY`, read only from the process environment, for the tests). `crates/runtime/examples/compile.rs` makes the payloads that `DISCORD-TEST.md` runs. The tests run the real binary against a fake HTTP server (exit codes, the marker token in no output, `SIGTERM` and `SIGINT` while connecting, the footer, `--reset-variable` on a real SQLite file, a changed variable type) and cover arguments, `.env`, assets, time stamps, redaction and the rate limit in unit tests, with a `proptest` run over arguments, `.env` text, asset paths and secrets. Checked by hand on a real test server on 2026-10-23 (commit `8b07c1f`) with `DISCORD-TEST.md`: rows 1, 2 and 3 (`Pong!`, a second start with no change), 8 and 9 (a rejected token and a bad server id, exit `2`, the token in no output), 10 (`SIGTERM`, `stopped`, exit `0`), 11 (a whole session in a file with the token in no line) and 12 (`--check`). Not run by hand: rows 4, 5, 6 and 7, which test the command diff, the deferral and the visibility in the adapter, which this change does not touch, and which its own tests cover. The gateway has no fake in the automated suite, so the close of the gateway and the wait for the runs are the manual rows. The only new dependencies are dev-only (`rmp-serde` and `zstd`, to build a payload of another version in a test).

- **M9. Export**. The new crate `crates/exporter` (it depends on `graph` only). `exporter::export` takes the runner executable, a `Payload`, the project folder (only its `assets/` is read), the output folder and the bot name, and writes `<name>` (the runner, the payload and the footer, mode 0755), `assets/` (a copy of the project's) and `.env.example` (`DISCORD_TOKEN=` and a commented `DISCORD_DEV_GUILD_ID=`, no value). It never writes a `.env`, a `data/` or a database, and never reads the project's `.env`. The name is a plain file name (at most 64 bytes, no leading dot or dash, no separator or control character, not `assets` or `data`). `assets/` is copied whole, regular files and folders only, nothing followed (a link or any other kind of file is refused and named), with limits of 4096 entries, 16 levels and 256 MiB **[measure]**; an asset that `requirements.assets` names and the project lacks refuses the export. A runner that already has a bot inside, a link or a file as the output, the project folder as the output and a place inside its `assets/` are refused. Everything is written to a staging folder inside the output and moved with renames, the executable last, after checks of what is already there (a folder where a file goes, a link where a folder goes), so an error leaves the output as it was and a folder the export created is removed. Exporting again replaces the executable (a rename, so it works while the old one runs), `.env.example` and the project's asset files, and keeps `.env`, `data/` and anything else; a test runs it while the real runner is up. `ExportError` is typed and names a path or a setting, never a value. `crates/exporter/examples/export.rs` writes a folder from a payload made by `examples/compile.rs`. `cargo xtask layers` has a new `dev_may_use`, and `runner` uses `exporter` only as a dev-dependency (a normal one still fails, with a test). The tests: `crates/exporter/tests/export.rs` (layout, modes, assets, missing asset, the token and databases of the project in no file, bad runner, bad payload, a second export with a `.env` and a `data/bot.sqlite` compared byte for byte, a running executable replaced, errors in the middle, links in the output, bad outputs and names, and a `proptest` run over arbitrary names that never writes outside the output) and `crates/runner/tests/export.rs` (the exported Ping dumps `ping.json`; the folder moved elsewhere starts with a cleared environment, makes `data/` with mode 0700, is exported again while it runs without touching `.env` or `data/`, and stops on `SIGTERM` with exit 0; a missing `.env`, the example copied as it is, and a missing asset exit 2 and say what is missing). The test helpers of the runner moved to `crates/runner/tests/common/`. Checked by hand on a real test server on 2026-10-23 with `DISCORD-TEST.md`: row 13 (`ldd` lists only libc, libm, libgcc_s and the loader; the folder copied to another place started with `env -i` from `/`, answered `Pong!`, made `data/` with mode 700 and stopped on `SIGTERM` with exit 0 and the token in no log line) and row 14 (no `.env` and the example copied as it is exit 2). Not run: the folder on a machine with another libc or no Rust toolchain at all; it ran in another directory with an empty environment on the same system. No new dependency.

- **M10a. Editor: project and canvas** (#13). The desktop app creates, opens and saves a project and edits its flows on a canvas. `graph` and `runtime` derive `specta::Type` (and `runtime::catalog` `Serialize`) behind an optional `specta` feature that only `apps/desktop` turns on; `cargo xtask bindings` generates the TypeScript types of the project and of the node schemas, in one shape per type (`disable_serde_phases`). The commands `new_project`, `open_project`, `save_project`, `validate_project` and `node_catalog` each have their own permission; the folder comes from a native dialog (`tauri-plugin-dialog`, only from Rust), stays in Rust, and the webview sends the project and never a path. Names, versions, positions and sizes are checked again in Rust, a new project needs an empty folder, and `validate_project` returns the diagnostics of `compile` with flow, node, field path and code. Rust tests: the `ping` sample saves back to identical bytes, and bad inputs (missing path, a link, a file, a damaged project, a newer `format_version`, bad names, a position that is not finite) return an error and write nothing. The frontend is a Svelte Flow canvas drawn from the project (positions kept), a palette built from the catalog, connect, move and delete with the lines the canvas cannot draw refused, a flow list, and open, new and save (`Ctrl+S`) with a refusal to leave unsaved changes. Every call goes through `TauriBackend` and Effect (`EditorStore` is the bridge, tested against `layerTest`); the edit helpers are pure and tested, including ids and aliases that never collide. Every text goes through `paraglide-js` (English), with the inlang plugin installed from npm, not a CDN. New dependencies: `tauri-plugin-dialog`, `@xyflow/svelte`, `@inlang/paraglide-js` and `@inlang/plugin-message-format` (dev). Checked by hand in the app on 2026-10-23: create, build Ping, connect, move, delete, save, reopen and several flows. Not in M10a: the property panel, undo and redo, and the diagnostics on the field (M10b), and a warning when the window closes with unsaved changes.

- **M10b. Editor: panel, undo and diagnostics** (#14). The editor gets a property panel, one undo history and diagnostics on the exact field. The panel is a right sidebar for the one selected node: its alias and a control for each field of its `NodeSpec` (`FieldControls`, recursive for the rows of a list), with no code per node type; labels come from `paraglide` and fall back to the field name, and a text field shows its length against its limit. The settings are edited by pure functions over the path that compile uses (`editor/settings.ts`: `setSetting`, `addRow`, `removeRow`, `renameAlias`); an emptied field, and an optional list left empty, is removed from `settings`. An alias is checked as it is typed and applied only when it is confirmed (Enter, or leaving the field): one that is not valid or is taken shows its message under the field and changes nothing, not even on the way; references are not rewritten (M11). The history (`editor/history.ts`) is one pure TypeScript stack of snapshots for the whole project, at most 200 steps: typing in one field of one node is one step (a selection change, a save, an undo or a redo closes it), a drag is one step, a new edit empties the redo side, and opening a project empties it. Undoing shows the flow the step touched, or the first when it is gone. `Ctrl+Z`, `Ctrl+Shift+Z`, `Ctrl+Y` and two toolbar buttons drive it, also inside a text field. "Unsaved" compares the project with the last opened or saved one by value (`editor/equal.ts`). After 300 ms without changes, and when a project is opened, the editor calls `validate_project` and drops an answer about a project that has since changed; `editor/diagnostics.ts` groups the result by field, node and line (`options[0].name` marks that row's field, `lines[n]` that line), and the toolbar counts the errors and warnings of the whole project. - **M11a. Condition builder: names, condition and renaming**. The part of the builder that lives in Rust, with the commands the interface will call. `runtime::compile::expression_names(project, flow, node)` lists what an expression of that node can read (`NameList`): the fields of the event, with the options of the command (an option the command does not require is `optional`), `steps.<alias>.<output>` of the nodes that run before it (`Sometimes` when only on some paths), the declared variables and `error.kind` and `error.message` after an `error` port. It uses the structure, dominators and event shape of `compile`, so a name that is offered is a name compile accepts there and one that is not offered is reported (`tests/names.rs` reads every offered name at the node and several that are not); a flow that is not sound offers no steps and says so (`order_known`). Each name has a `ValueKind` (text, integer, decimal, boolean, list or any): `TriggerSpec::fields` is now a list of `EventField` with a kind, `OutputSpec` has a kind, and `TriggerSpec::event_names` gives both compile and the builder the same fields. `runtime::condition::Condition` is the model: rows joined by *all* or *any*, each a comparison (`== != < <= > >=`), a text test (`contains`, `startsWith`, `endsWith`, optionally negated), a membership (`item in list`, optionally negated) or a presence test (`has(name)`, optionally negated), with names, text, whole numbers up to 2^53 and decimals as operands, at most 8 rows. `to_source` writes the CEL (text as a quoted literal with its quotes, backslashes and control characters escaped, so typed text is data and never code; a name that is not an identifier as `event.options["mi-opción"]`) and checks it compiles; `from_source` reads an expression back and returns `None` for any other shape (`!(a == b)`, nested `&&` and `||`, `size(...)`, macros, arithmetic, a number past 2^53, bytes), so the advanced mode keeps those as text. `from_source(to_source(c)) == c` is a `proptest` property over arbitrary rows, text and numbers, the real conditions of Welcome and Moderation are read and written back, and a table of hostile text (`a" || true || "`, backslashes, line breaks, NUL, `{{ }}`) stays one literal and evaluates to itself. `ExpressionEngine` has two new methods, `syntax` (a `Syntax` tree without any `cel` type) and `rename_step`; `cel_engine` is now a folder (`convert`, `rename`) that is still the only code that uses `cel`. `runtime::rename::rename_alias` gives a node an alias and rewrites every `steps.<old>` in the expressions and in the `{{ }}` segments of the templates of its flow, also inside the rows of a list. The reads are found in the token stream and checked against the syntax tree: the rewritten source must parse to the original tree with exactly the reads of the old alias renamed, or the field is refused, so a string that says `steps.old`, `event.options.steps.old`, `steps.older`, `steps.other.old`, a macro variable and the text around a `{{ }}` are never touched (offsets inside macros are not reliable in `cel`, which is why the tree and not the offsets decides). The alias must be valid and free; a field that does not compile yet, a macro variable called `steps` or a text that would pass its limit is left as it is and reported in `left_alone` with the reason, and compile then marks the read that points at nothing. The commands `expression_names`, `condition_to_source`, `condition_from_source` and `rename_alias` of `apps/desktop` validate their input in Rust, each has its own permission, and they return typed errors; the TypeScript types are generated (`bindings`) and the end-to-end catalog is updated. Not in M11a: any interface (M11b).

- **M11b. Condition builder: interface**. The panel edits a condition from lists and renames a node with its reads. A new kind of field, `FieldKind::Condition` (an expression that gives true or false), is the one the builder is offered for; `logic.branch` uses it, and `data.set_variable` keeps `Expression`, so there is no code per node type. A `Condition` field has two modes. The **builder** (`ConditionBuilder`, `OperandPicker`) shows one row per test: the left side picked from the names of `expression_names`, grouped (event, earlier steps, variables, error) with *optional* and *only on some paths* marked, a test offered by the kind of the left side (`editor/condition.ts`: comparisons for numbers, text tests for text, *includes* for a list, *is set* for an optional name `has()` can test), and the right side from the same list or typed in as text, a whole number, a decimal or true/false; at most 8 rows, *all* or *any*, and the expression Rust writes (`condition_to_source`) always shown under the rows. The **advanced mode** is CodeMirror 6 used directly (`CodeEditor`, loaded with a dynamic `import()` the first time an expression is shown), edits the same text and completes the names of the node as they are typed; `data.set_variable`'s `value` uses it alone. Going to the advanced mode keeps the text; going back works only when `condition_from_source` reads it, and otherwise a note says so and the editor stays (an undo that brings back a shape the builder cannot show also moves to the advanced mode). The project still stores only the text. **CodeMirror and the CSP:** it writes its styles into a `<style>` element, which `style-src 'self'` forbids, and the end-to-end tests with the production CSP caught it; the editor now lives in a shadow root, where CodeMirror uses a constructed stylesheet, so the CSP stays as it was, with no `unsafe-inline` and no nonce. **The history:** a choice from a list is a step of its own and text typed into a box is joined into one step (`EditorStore.setSetting(..., join)`); `Ctrl+Z` also works inside CodeMirror, whose own history is not loaded. **Renaming:** `EditorStore.renameAlias` checks the alias as before, then calls `rename_alias` and replaces the project in one step, so one `Ctrl+Z` brings back the alias and every expression; if the project changed while Rust answered it asks again (3 times at most); a field Rust left alone is named in a notice with its reason; a refusal changes nothing. **A broken read:** the names offered are the names compile accepts, so a name of a row that is not in the list is marked on the row (*not available here*, in red) and shown as such in the menu without being changed, and compile's own message stays under the field; where the order of the flow is not known the `steps` and `error` names are not reported. The calls `expressionNames`, `conditionToSource`, `conditionFromSource` and `renameAlias` are in `TauriBackend` (and its test layer). Tests: `vitest` covers the pure functions of the builder (`editor/condition.ts`: the tests of every kind of row, changing a row into another kind, what to offer by kind, a name that is missing, the rows and the limit), the store (rename as one step with its undo, notice for a field left alone, a failed call, a project that changed meanwhile, reading and writing a condition, the names of the selected node and a stale answer, a choice versus typing in the history) and the four calls of `TauriBackend` through `mockIPC` (names, arguments, an error of Rust kept); the end-to-end test (`e2e/specs/condition.e2e.ts`, on a fake backend whose condition commands are small stand-ins for the Rust ones, which have their own tests) builds a condition from lists and reads the expression, edits it in CodeMirror and takes it back to the builder, sees a shape the builder cannot show stay as text, completes a name, undoes typing in the editor, renames a node and sees the expression change and come back with `Ctrl+Z`, and deletes the node and sees the row and the field marked, with no CSP violation. New dependencies: `@codemirror/state`, `@codemirror/view`, `@codemirror/commands` and `@codemirror/autocomplete` (MIT, pinned; the editor ships as its own chunk of about 300 kB, 98 kB gzipped). **Not checked:** the real WebKitGTK window of Tauri (that CodeMirror's constructed stylesheet and the lazily loaded chunk work there, and a release build with its CSP; a defect found there is fixed under this milestone) and use with the keyboard alone, which rests on native controls and was not driven by a test. Not in M11b: declaring variables, the *Text template* node and its insert button (M13), typing the operands, and nested conditions (`a && (b || c)` stays in the advanced mode).

- **M12a. Local run and export: backend** (M12 was split in two: this is the Rust side of `apps/desktop`, the interface is M12b and the tests of the real app are M12c). `supervisor.rs` runs the runner as a child with `tokio::process`: a cleared environment with only the variables it is given, standard input closed, `kill_on_drop` as a last resort. It reads standard output and error with a bounded line reader (64 KiB a line, the rest of a longer one dropped) and emits typed events in order: `Log` (a `LogLine`; a line that is not one, invalid UTF-8 and a huge line become `warn` lines of source `engine` with the text cut, and every text field of a record is cut to its limit), and `Status` (`starting`, `running` at the first line of output, `stopping`, `exited` with the code, the signal, a reason from §9.3 and whether the person asked). A line of standard error, where the `error:` line of a failed start goes, is an `error` line. `stop` sends `SIGTERM` with `rustix::process::kill_process` (safe) and kills after 10 seconds; with nothing running it says so, and the slot is free again as soon as the exit has been reported. The sidecar decision changed: the runner is still bundled as `externalBin` but started with `tokio::process`, not `tauri-plugin-shell`, whose child can only be killed (`DECISIONS.md`); the app stops the bot when it exits. `run.rs` has the commands. `start_bot` takes the project the webview shows, compiles it in Rust and, with an error, starts nothing and returns the diagnostics; otherwise it writes `.botinventor/run/payload.bin` (a temporary file and a rename, mode 0600, a link in the local folder refused) and starts the runner with exactly `BOT_INVENTOR_PAYLOAD`, `BOT_INVENTOR_ENV_FILE`, `BOT_INVENTOR_ASSETS_DIR` and `BOT_INVENTOR_DATA_DIR`. `set_token` and `set_dev_guild` write `.env` (`dotenv.rs`) through a temporary file and a rename with mode 0600 whatever the old file had, keep its other lines, and refuse a link, a folder or a file over 64 KiB; a token must be 1 to 256 of `A-Z a-z 0-9 . _ -` and a server id 1 to 20 digits, so neither can add or change another line. `token_status` returns whether a token is set and the server id. `Token` has no `Debug` output of its value, and no command, event, error or log line has the token (a test with a marker token calls them all and searches what they return). `export_bot` checks the name, asks for the output folder with the native dialog (the folder stays in Rust), compiles like `start_bot` and calls `exporter::export` with the bundled runner; the logic is `export_in`, a plain function over a folder. Each command has its own permission and the window's capability lists no plugin permission (a test reads it). `cargo xtask dev`, `build`, `lint`, `test` and `bindings` build the runner and copy it to `apps/desktop/src-tauri/binaries/runner-<target triple>` (ignored by git; `build` uses the release runner), because the Tauri crate does not compile without it. Tests: for the supervisor, a stand-in shell script for the runner (the environment is cleared, 10 000 lines in order, odd output, cut text, every exit code and a signal, `SIGTERM` obeyed at once, a child that ignores it killed after the grace period, a second start refused, a program that does not start, and no child left when the runtime is dropped); for the files, the token, the server id, the repeated key, a link, a folder, a huge file, hostile text and a `proptest` run in which a written `.env` differs from the old one in the token line only; for the commands, the payload and the exact environment, a project with errors, a folder that has gone, a link in the local folder, and the real runner exporting a bot whose `--dump` equals the payload a local run wrote, with no `.env`, no `data/` and no token in any exported file. New dependencies: `rustix` (`process` only, already in the tree), `tokio` (`process`, `io-util`, `rt`, `sync`, `time`, `macros`) and `tempfile` (already used by tests) in `apps/desktop`, and `exporter` as a dependency of the app, which `cargo xtask layers` allows. `cargo xtask build` on 2026-10-24 produced the `.deb`, the `.rpm` and the AppImage, and the `.deb` and the AppImage hold `usr/bin/runner` next to `usr/bin/desktop` (the place `bundled_runner` looks); the extracted AppImage's runner answers `--version`. **Not checked:** the real window (that closing it stops the bot, and `start_bot` from the webview) and a package installed with the runner started from the installed app, which are M12c.

- **M12b. Local run and export: interface** (#18). The editor gets what M12a built. `TauriBackend` has `startBot` (it makes the `Channel` and nothing else touches it), `stopBot`, `setToken`, `tokenStatus`, `setDevGuild` and `exportBot`, with a test layer and `mockIPC` tests of the names, the arguments, the order of the events (also delivered out of order) and an error of Rust kept. `RunStore` (`app/run.svelte.ts`) follows the bot (`idle`, `starting`, `running`, `stopping`, `exited`), locks the editor (`EditorStore.locked`) so that opening or creating a project cannot replace the one that runs, and starts the project as it is shown; *Run* is disabled with no project, while a bot runs and while live validation counts an error, and a project that Rust finds invalid shows its error count and validates again. An exit is told in words (`app/exit.ts`), and one nobody asked for says so. The log (`editor/logs.ts`) is a buffer of the last 5000 lines that counts the dropped ones; lines are queued and added every 16 ms, so a burst costs one update. The panel (`LogPanel`) shows time, level as a word, source, flow and node, follows the newest line until the person scrolls up (*Jump to latest*), has *Clear*, and starts collapsed so it takes no room while the bot is edited and opens when the bot starts. Its text is always inserted as text. *Bot settings* (`BotSettings`) has a password field for the token with `autocomplete="off"`, read from the element when it is sent and emptied at once, with or without an error; it is the argument of one call and is in no store, history, notice, storage or page (`vitest` searches the store, the notices and the failure texts for a marker token, and an end-to-end test searches the page, its attributes and `localStorage`); the state says *A token is set* or *No token yet*, and the development server is saved, refused with Rust's message and removed from the same dialog. *Export* (`ExportDialog`) offers a name made from the project's (`defaultBotName`), shows Rust's message for a bad one, asks for the folder only after the name is accepted, changes nothing when the folder dialog is cancelled, and explains a project with errors without writing. The dialogs are native `<dialog>` elements: Enter and Escape work and the focus goes back to the button that opened one. Every text goes through `paraglide`. The end-to-end window is 1500x950, and the specs of running and exporting open a prepared Ping instead of building it, because where a drag lands depends on the size of the canvas. No new dependencies. **Not checked:** the app against a real Discord server (the bot itself was checked that way in M7, M8 and M9; here it runs through the supervisor of M12a, which its own tests cover), and the real window of Tauri, which is M12c.

## 5. Later, and not planned

**Later** (wanted, no plan yet): Windows and macOS builds with code signing; export for another system than the current one; other interface languages; automatic updates; optional embedding of assets in the executable; Rust code generation as an advanced export; other platforms (Telegram, Twitch, Slack) through the `Platform` trait.

**Not planned:** a code or script node (the bot is strictly no-code); plugins or third-party nodes (they need their own security design); voice and audio; sharding for very large bots; hosting the bots (the user runs the exported bot on their own machine or server); real-time collaboration, a marketplace or accounts (not part of a local-first tool).
