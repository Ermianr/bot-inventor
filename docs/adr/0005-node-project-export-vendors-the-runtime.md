# Node Project Export vendors the Runtime as source

A Node Project Export is a folder someone reads, versions and hand-edits (issue #9), so the generated code cannot import `@bot-inventor/runtime` the way a Build does: the Runtime is a private workspace package and there is nothing on npm for `npm install` to fetch. We decided that **an Export copies the Runtime's compiled JavaScript into `src/runtime/` and the generated Flows import it by relative path**, rather than publishing the Runtime to npm or bundling it into the Export the way [ADR 0004](./0004-single-file-export-is-an-esbuild-esm-bundle.md) does for the Single File.

Publishing was rejected because it would tie a bot someone exported to a registry and a release cadence we would then have to keep forever; bundling was rejected because readability *is* this format's feature, and a bundled blob in the middle of the folder is exactly what the format exists to avoid.

## Consequences

- **The Export's dependencies are the Runtime's own, read from its manifest**, plus `dotenv` for the entry point. They are never written down in the Compiler: a hard-coded range could ask npm for a discord.js the vendored code beside it has never run on. A range containing `:` — `workspace:`, `catalog:` — fails the Export loudly here rather than failing `npm install` in the user's folder.
- **The Runtime must be built before an Export can be written.** The Compiler copies `dist`, not `src`, so the Export carries plain ESM with its comments intact and no TypeScript. Resolving the Runtime is what fails when it has not been built, because its `exports` points into `dist`, and that is the failure the Export names.
- **`testing.js` is excluded**; declarations and source maps stay behind. The fake Runtime our own tests run against has no business in a bot someone hosts, and a source map the Export did not copy would only dangle.
- **Anything else in the Runtime's build stops the Export.** The copy is one level deep and knows only about `.js`. A Runtime that starts emitting a subdirectory or an asset would otherwise produce a folder that is quietly incomplete and fails on `npm start` in the user's hands rather than here, which is the one place the mistake can still be fixed.
- **`package.json` is written last and the directories the Export owns are emptied first.** The marker file is what makes a second Export refuse, so a half-written folder must not carry one; and a Flow the user renamed must take its file with it, or the folder they commit keeps a dead module that still looks live.
- **The Export is a fork the moment it is written.** Nothing links the copied Runtime back to Bot Inventor, so a user's hand-edits survive until they Export again, and a Runtime fix reaches them only by exporting again. The README says so, because a folder that silently went stale would be worse than one that says it is a copy.
- **`.env` is how the token reaches the bot**, which is what `dotenv` buys: a Single File is handed its environment by whoever runs it, but a folder in version control needs somewhere to put the token that is not a file it commits. The Export ships an `.env.example` and a `.gitignore` naming `.env`.
