# The application owns Project files

A Project only became real once the user picked a folder in a system Save dialog, and it survived only as long as they remembered to press Save. That is the file-manager model — the user owns the document, the application edits it — and it asks somebody who came to build a Discord bot to first have an opinion about folders. We decided instead that **the application owns Project files**: it keeps every Project under its own data directory, one folder per Project keyed by the Project's id, and the user never types or picks a path to work.

The alternative was to keep the document model and soften it with a recent-files list. It would have left every failure the current model has — a Project moved on disk, a Project saved nowhere, a window asking about changes the user did not know they had — in exchange for a shortcut to the file dialog. Owning the storage removes the questions instead of answering them faster.

## Consequences

- **Work saves itself.** There is no Save, no Save As, and no guard on closing. This removes the user's cheapest undo — closing without saving — and nothing here replaces it. Undo on the Canvas is the right answer, and this decision is what makes it worth building.
- **The Dashboard is the root screen.** The application no longer opens onto a Canvas holding a Project nobody asked for; the editor lives under a route carrying a Project id. There is no "the Project that is open at startup", so the initial-project module goes, and the demonstration Project survives as what the empty Dashboard's example button creates.
- **`.botinv` is demoted to an interchange format.** It stops being the document the user manages and becomes the shape a Project takes when it leaves. Share writes one to a path the user chooses; Import copies one in and rewrites its id, so importing the same file twice yields two independent Projects and an import can never overwrite existing work. Save and Open leave the Menu Bar; Share and Import take their place, and Export keeps meaning what it meant — writing the result of a Build.
- **One folder per Project is the unit of deletion.** The `.botinv` document and the machine-local settings for that Project — the Test Server first among them — sit side by side, so deleting a Project is deleting one folder and there is no second place for a stray file to survive. There is no `index.json`: the Dashboard reads name, id and last-changed from the Project documents themselves rather than from a second source of truth that drifts the first time something fails halfway.
- **No domain term is introduced for the storage.** The Dashboard shows Projects; the directory is called `projects/` and stays an implementation detail. A glossary entry that is the plural of another glossary entry would make every sentence using it ambiguous.
- **The Rust side keeps owning the paths.** A new module owns `projects/`, the way the existing jail module owns what it guards; the webview never invents a path. The Project-file module narrows to Share and Import, the only two cases left where a user picks one.
- **There is no backwards compatibility.** Pre-v1, a `.botinv` written by an earlier build may be refused outright, and Projects living outside the application from the old manual-save flow are not discovered, adopted or migrated. The `schemaVersion` migration machinery in `packages/schema` is untouched: this decision is about the storage model, not about the document format.
